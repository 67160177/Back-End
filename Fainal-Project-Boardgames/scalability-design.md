# Scalability Design (สัปดาห์ที่ 14)

เอกสารนี้ตอบคำถาม "ถ้าข้อมูลหรือผู้ใช้เพิ่มขึ้นมาก ส่วนไหนของระบบจะมีปัญหาก่อน และจะแก้อย่างไร" โดยใช้ตัวเลขที่วัดจริง ไม่ใช่การคาดเดา

## 1. ผลวัดจริงเมื่อข้อมูลโตขึ้น

วัดบน MySQL 8.0.46 (Docker) เครื่องเดียวกับที่ใช้พัฒนา ด้วย SQL ชุดเดียวกับ `GET /api/v1/boardgames` ใน `src/index.js`
สร้างฐานข้อมูลชั่วคราวด้วย `npm run migrate` ใส่บอร์ดเกม (เกมละ 2 หมวดหมู่ จาก 20 หมวด) แล้ววัดค่ากลางของ 3 รอบ

| จำนวนบอร์ดเกม | หน้า 1 (20 รายการ) เรียงตาม id | หน้า 1 เรียงตามชื่อ | หน้า 1 กรองหมวดหมู่ | **แบบเดิม: ส่งทุกแถว** (ก่อนมี pagination) |
| --- | --- | --- | --- | --- |
| 1,000 | 4.8 ms / 2 KB | 4.6 ms | 0.9 ms | 3.6 ms / 103 KB |
| 10,000 | 39.9 ms / 2 KB | 40.8 ms | 2.9 ms | 29.2 ms / **1 MB** |
| 100,000 | **560 ms** / 2 KB | 564 ms | 26.5 ms | 288 ms / **10.5 MB** |

ตอนนี้มีข้อมูล 3 เกม ถ้าโต **10 เท่า (30 เกม)** ระบบไม่มีปัญหาเลย จุดที่เริ่มรู้สึกได้คือหลักหมื่นถึงแสนรายการ

### สิ่งที่ตัวเลขบอก

1. **Pagination ช่วยฝั่งเครือข่ายและหน้าเว็บได้มาก**: ข้อมูลที่ส่งกลับลดจาก 10.5 MB เหลือ 2 KB ที่ 100,000 เกม
   ถ้าไม่มี pagination เบราว์เซอร์ต้องโหลดและวาดรายการแสนแถว ซึ่งช้ากว่าตัวฐานข้อมูลอีกหลายเท่า
2. **แต่ pagination ตอนนี้ยังไม่ได้ลดงานของฐานข้อมูล**: เวลาโตตามจำนวนข้อมูลแบบเส้นตรง (10 เท่าของข้อมูล ≈ 10-14 เท่าของเวลา)
   `EXPLAIN` แสดงว่า MySQL อ่าน `boardgames` ทั้งตาราง (`type=ALL`) จัดกลุ่ม `GROUP_CONCAT` ทุกเกม แล้วจึงตัด `LIMIT 20`
   เพราะต้องรู้หมวดหมู่ของทุกเกมก่อนจะเรียงและนับ `COUNT(*) OVER()`
3. **การกรองตามหมวดหมู่เร็วกว่ามาก** (26 ms ที่ 100,000 เกม) เพราะ `WHERE c.id = ?` ลดจำนวนแถวก่อนจัดกลุ่ม และใช้ index ของ FK

## 2. จุดที่จะมีปัญหาก่อน เรียงตามลำดับ

| ลำดับ | จุด | เกิดเมื่อ | อาการ | วิธีแก้ |
| --- | --- | --- | --- | --- |
| 1 | `GET /api/v1/boardgames` ไม่กรองหมวดหมู่ | ~50,000 เกมขึ้นไป | หน้าแรกช้าเกินครึ่งวินาที | (ก) **แบ่งหน้า 2 ขั้น**: เลือก `id` 20 ตัวของหน้านั้นจากตาราง `boardgames` อย่างเดียวก่อน (ใช้ PK / UNIQUE index ของ `name` ได้) แล้วค่อยดึงหมวดหมู่เฉพาะ 20 เกมนั้น และนับ `COUNT(*)` แยก (ข) เพิ่ม index ให้คอลัมน์ที่เรียงได้ (`created_at`, `minPlayers`, `maxPlayers`) ด้วย migration ไฟล์ใหม่ (ค) cache ช่วยได้แล้วตอนนี้ คำขอซ้ำภายใน 30 วินาทีไม่ถึงฐานข้อมูล |
| 2 | `POST /api/v1/boardgames` รอส่งแจ้งเตือนก่อนตอบ | Discord ช้า/ล่ม หรือเพิ่มเกมพร้อมกันมาก | ตอบช้าสุด ~7.6 วินาที (retry 3 รอบ) และกิน connection ของ Gateway | เปลี่ยนเป็น asynchronous: บันทึกเหตุการณ์ลง message queue (เช่น RabbitMQ) แล้วตอบ 201 ทันที ให้ notification-service อ่านจากคิวเอง |
| 3 | state ที่อยู่ในหน่วยความจำของ process | รันแต่ละ service มากกว่า 1 instance | cache ไม่ตรงกันระหว่าง instance, rate limit นับแยกเครื่อง (โควตาจริงคูณตามจำนวน instance), ประวัติแจ้งเตือนหายเมื่อรีสตาร์ท | ย้ายไป Redis ที่ใช้ร่วมกัน: cache (`src/cache.js`), store ของ `express-rate-limit`, ประวัติแจ้งเตือน |
| 4 | MySQL เครื่องเดียว | อ่านมากจน CPU ของฐานข้อมูลเต็ม หรือเครื่องฐานข้อมูลล่ม | ทุก service ที่ใช้ฐานข้อมูลช้า/ล่มพร้อมกัน | read replica สำหรับ GET (ระบบนี้อ่านมากกว่าเขียนมาก), connection pool ต่อ instance (ตอนนี้ 10) ต้องคิดรวมไม่ให้เกิน `max_connections` |

## 3. อะไรขยายแนวนอน (horizontal scaling) ได้แล้วบ้าง

| ส่วน | เพิ่ม instance ได้เลยไหม | เหตุผล |
| --- | --- | --- |
| API Gateway | ได้ (ต้องย้าย store ของ rate limiter ไป Redis ก่อน) | ไม่มี session หรือข้อมูลผู้ใช้ เป็นแค่ตัวส่งต่อคำขอ |
| boardgame-service | ได้ (ต้องย้าย cache ไป Redis หรือยอมให้แต่ละ instance มี cache ของตัวเองที่อายุสั้น) | ข้อมูลทั้งหมดอยู่ใน MySQL ไม่มี state อื่น |
| notification-service | ได้ แต่ประวัติจะแยกกันอยู่ | ประวัติเก็บในหน่วยความจำ ควรย้ายไปฐานข้อมูล/Redis |
| MySQL | ไม่ได้โดยตรง | ต้องทำ replication (อ่าน) หรือแยกฐานข้อมูลตาม service |

ถ้าเพิ่มระบบ login ภายหลัง ควรใช้ JWT แบบ stateless เพื่อให้ instance ไหนก็ตรวจ token ได้โดยไม่ต้องแชร์ session

## 4. สิ่งที่ทำไปแล้วในโปรเจกต์เพื่อรองรับการโต

| สิ่งที่ทำ | อยู่ที่ |
| --- | --- |
| Pagination (`page`, `limit` สูงสุด 100) และ Sorting ที่เรียงคงที่ (`id` เป็นลำดับรอง) | `GET /api/v1/boardgames` ใน `src/index.js` |
| Cache ผลของ GET 30 วินาที ล้างทันทีเมื่อมีการเปลี่ยนแปลง และจำกัด 100 รายการ | `src/cache.js` |
| Rate limiting ต่อ IP ที่ Gateway | `gateway/index.js` |
| Connection pool ของ MySQL (ไม่เปิด connection ใหม่ทุกคำขอ) | `db.js` |
| Timeout + Retry + Fallback เมื่อเรียก service อื่น ไม่ให้ service ช้าลากระบบค้าง | `src/services/external-api.js`, `gateway/index.js` |
| Migration แบบมีเวอร์ชัน เปลี่ยนโครงสร้างฐานข้อมูล (เช่นเพิ่ม index) ได้อย่างเป็นระบบ | `migrations/`, `scripts/migrate.js` |

## 5. วิธีวัดซ้ำ

1. สร้างฐานข้อมูลชั่วคราว: `DB_NAME=boardgame_scale_test npm run migrate`
2. ใส่ข้อมูลจำนวนมากด้วย `INSERT ... VALUES ?` ทีละ 5,000 แถว แล้ววัดเวลา SQL ของ `GET /api/v1/boardgames` (ค่ากลางของ 3 รอบหลัง warm up)
3. ดูแผนการทำงานด้วย `EXPLAIN` เพื่อหาว่าอ่านทั้งตาราง (`type=ALL`) หรือใช้ index
4. ลบฐานข้อมูลชั่วคราวเมื่อเสร็จ: `DROP DATABASE boardgame_scale_test;`
