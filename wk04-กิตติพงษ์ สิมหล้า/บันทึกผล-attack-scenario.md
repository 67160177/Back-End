# บันทึกผลการทดสอบ Attack Scenario พื้นฐาน

## 3.4 การทดสอบ Payload ขนาดใหญ่ผิดปกติ (Oversized Payload)

### วิธีทดสอบ

ส่งคำขอ `POST /api/v1/students` พร้อม field `name` ที่มีขนาดข้อมูลประมาณ 15KB โดยสร้างข้อความยาวด้วย Pre-request Script ใน Postman:

```javascript
pm.variables.set("longName", "x".repeat(15000));
```

จากนั้นใช้ตัวแปรนี้ใน body ของคำขอ ซึ่งมีขนาดรวมเกินขีดจำกัดที่ตั้งไว้ในโค้ดฝั่งเซิร์ฟเวอร์ที่ `express.json({ limit: "10kb" })`

### ผลการทดสอบ

เซิร์ฟเวอร์ตอบกลับ **Status Code 413 Payload Too Large** ตรงตามที่คาดหวัง พร้อม error body ดังนี้:

```json
{
  "error": {
    "code": "entity.too.large",
    "message": "request entity too large"
  }
}
```

### ข้อสังเกต

- ระบบสามารถป้องกันการโจมตีลักษณะส่ง payload ขนาดใหญ่ผิดปกติได้อย่างมีประสิทธิภาพ โดย middleware `express.json({ limit: "10kb" })` จะปฏิเสธคำขอตั้งแต่ชั้นแรกสุด

## 3.5 การทดสอบ Type Confusion

### วิธีทดสอบ (ตามที่ตั้งใจ)

ส่งคำขอ `POST /api/v1/students` โดยกำหนดให้ field `name` เป็นอ็อบเจกต์แทนที่จะเป็นข้อความ (string) เพื่อดูว่าระบบตรวจสอบชนิดข้อมูล (type) ของอินพุตหรือไม่:

```json
{
  "name": { "malicious": "payload" },
  "major": "วิทยาการคอมพิวเตอร์",
  "email": "test2@example.com"
}
```

### ผลการทดสอบ

**ไม่สามารถทดสอบได้สมบูรณ์ผ่านการยิงคำขอจริง** เนื่องจากระหว่างตรวจสอบซอร์สโค้ดพบว่า route `POST /api/v1/students` (รวมถึง route อื่นทั้งหมดของระบบ) ถูกประกาศไว้ **หลัง** 404 handler (`app.use((req, res) => {...})`) ในไฟล์ `index.js` ทำให้ Express จับคู่ทุกคำขอเข้ากับ 404 handler ก่อนเสมอ ส่งผลให้ route ที่ประกาศไว้ด้านล่างไม่ถูกเรียกใช้งานเลย ไม่ว่าจะยิง method หรือ path ใดก็ตาม

### ข้อสังเกต

- หากส่ง `name` เป็นอ็อบเจกต์ (`{ "malicious": "payload" }`) เงื่อนไข `!name` จะมีค่าเป็น `false` เนื่องจาก object ที่ไม่ใช่ `null`/`undefined` ถือเป็นค่า truthy เสมอ
- ช่องโหว่นี้ยังไม่ได้รับการแก้ไขในโค้ดปัจจุบัน ตามแผนของรายวิชาจะได้รับการแก้ไขอย่างเป็นระบบด้วยไลบรารี **Zod** ในสัปดาห์ที่ 13
