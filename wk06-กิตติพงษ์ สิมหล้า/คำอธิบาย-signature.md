# เหตุใด Token ที่ถูกแก้ไขจึงถูกปฏิเสธ

JWT (JSON Web Token) ประกอบด้วย 3 ส่วน ได้แก่ **Header, Payload และ Signature** โดย Header และ Payload จะถูกแปลงเป็นรูปแบบ Base64URL แล้วนำมาสร้าง Signature โดยใช้ Secret Key ของเซิร์ฟเวอร์และ Algorithm ที่กำหนดไว้

เมื่อเซิร์ฟเวอร์ได้รับ Token จะนำ Header และ Payload ที่ได้รับมาคำนวณ Signature ใหม่ด้วย Secret Key เดิม แล้วนำไปเปรียบเทียบกับ Signature ที่แนบมากับ Token

หากมีการแก้ไขข้อมูลใน Token แม้เพียงตัวอักษรเดียว เช่น การเปลี่ยนค่า `role` หรือข้อมูลของผู้ใช้ Header หรือ Payload จะเปลี่ยนไป ส่งผลให้ Signature ที่คำนวณใหม่แตกต่างจาก Signature เดิมทันที เนื่องจาก Signature มีความสัมพันธ์กับข้อมูลภายใน Token และ Secret Key ของเซิร์ฟเวอร์

ดังนั้น ผู้ที่แก้ไข Token โดยไม่มี Secret Key จึงไม่สามารถสร้าง Signature ที่ถูกต้องขึ้นมาแทนได้ เมื่อ Signature ไม่ตรงกัน เซิร์ฟเวอร์จะถือว่า Token ไม่ถูกต้องหรืออาจถูกดัดแปลง และปฏิเสธคำขอโดยตอบกลับสถานะ **401 Unauthorized** พร้อมข้อความ `INVALID_TOKEN`

ดังนั้น **Signature** จึงมีหน้าที่สำคัญในการตรวจสอบ **ความถูกต้องและความสมบูรณ์ของข้อมูล (Integrity)** ภายใน JWT และช่วยป้องกันการปลอมแปลง Token เพื่อเข้าถึงสิทธิ์ของผู้ใช้อื่น

> **หมายเหตุ:** JWT แบบทั่วไปไม่ได้เข้ารหัส Payload เพื่อปกปิดข้อมูล แต่ใช้ Signature เพื่อยืนยันว่าข้อมูลไม่ได้ถูกแก้ไข ดังนั้นจึงไม่ควรใส่ข้อมูลลับหรือข้อมูลสำคัญที่ไม่ต้องการเปิดเผยไว้ใน Payload
